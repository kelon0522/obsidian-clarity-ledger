## Clarity Ledger · install.bat 跑不了（行尾符）

用户报 `install.bat` 双击后刷出几十条 `'xxx' 不是内部或外部命令`。

### 根因

**文件是 LF 行尾，而 `.bat` 必须是 CRLF。**

cmd.exe 按 CRLF 切分命令，遇到 LF 会把相邻行**错位拼接**，于是：

```
REM  Clarity Ledger - install into an Obsidian vault (Windows)
```

被截成两半、分别当成命令 → `'larity' 不是内部或外部命令`、`'al' 不是内部或外部命令`。

**报错信息与真实原因隔得非常远** —— 第一反应必然是「脚本内容写错了」，
而内容一个字都没错。这个坑作者自己也在文件头写过注释（编码相关），
但当时只考虑了**编码**、没考虑**行尾**。

这个 bug 本机复现不了：`core.autocrlf=true` 时 git 检出会自动把 LF 转 CRLF，
所以作者自己跑永远正常，只有 clone 下来的人会炸。

### 顺带发现第二个坑：非 ASCII

文件里有一行 `echo Then walk through 手测清单.md` —— 是我上一版加的，
**破坏了原作者「Everything here is deliberately ASCII」的约定**
（.bat 按系统 ANSI 代码页 cp936 读，UTF-8 中文会变乱码）。

讽刺的是我写这次修复说明时，第一版注释里**又写了中文文件名**，
当场被自己的检查脚本抓出来。

### 修法

- `install.bat` 行尾 LF → CRLF（129 行）
- 新增 `.gitattributes` 从根上锁死，不靠各人本机配置：
  `*.bat text eol=crlf`、`*.sh text eol=lf`
- 新增 `scripts/check-bat.mjs`（`npm run check:bat`），五条断言：
  CRLF、无 `\r\r\n`、纯 ASCII、无 BOM、首行 `@echo off`。并入 `npm run build`。

## 我自己造成的回归（值得记）

给 `package-lock.json` 加了 `-text` 然后跑 `git add --renormalize`，结果：

1. **lock 丢条目** —— 少了 `@csstools/css-tokenizer` 等，

   `Cannot find package '@csstools/css-tokenizer'`，
   **一条用例都没失败**，只有 `Errors 4 errors`。
   极易误判成「测试脚本坏了」。

已去掉 lock 的特殊规则，教训写进 `.gitattributes` 与 CONTRIBUTING。

## 顺带修好：lock 的第二类坏条目

`fix-lock-optional.mjs` 早先只处理「连 version 都没有」的空壳，
漏了「有 version 但缺 `resolved`/`integrity`」的那类
（`@csstools/css-tokenizer` 就是这种，npm 要解析 peer 元数据才写得全）。

判据不能只看 `!v.version`。两类都要处理，且情况 B 必须**就地补字段**而非整条替换
——那些条目身上有 `peer: true` 等字段，整条覆盖会让 lock 依然不同步。

本次补了 **130 个条目**（远超原先的 22 个）。

## 写断言脚本时它自己崩了（第二次栽在同一类坑）

`check-bat.mjs` 第一版有 `new Set(x).map(...)` —— Set 没有 map，抛 TypeError。
而这个 TypeError 发生在**构造错误消息的表达式**里，
于是「非 ASCII 检查」这条最该抓乱码的断言自己先崩了、永远报不出结果。

修法：`ok()` 的 detail 改成**传函数**，惰性求值 + try/catch 包住，
构造消息的异常会明确报成「这条断言本身有 bug」。

结论：**错误消息本身也要测**。`{ ok }` 那层包装包不住构造消息的代码。

### 问题 2：详情页的 `English | 中文` 是怎么做的

**机制：Obsidian 详情页只渲染 `README.md` 这一个文件**，没有「加载第二个 md」的能力。
那一行切换靠的是 **Obsidian 会把 README 里的相对链接重写成 GitHub 仓库地址**
—— 所以写法必须是 `./README.zh-cn.md`，不能写成完整 URL

做法（**直接参照已上架的 Remotely Save 插件**，拉了它的 README 源码确认）：

```markdown
# Clarity Ledger

English | [中文](./README.zh-cn.md)
```

- `README.md` = 英文（Obsidian 渲染的就是它，所以必须是英文）
- `README.zh-cn.md` = 中文，顶部 `[English](./README.md) | 中文` 反向切回
- 点「中文」跳 GitHub，看中文版文件

### 关键事实（写清单时核实的）

- `manifest.version` = `0.1.0`，`versions.json` = `{"0.1.0": "1.5.0"}`，**还没有 tag**
- `main.js` / `styles.css` **故意不在仓库里**（`.gitignore` 明确写了）——
  Release 流水线会现构建。远端只有 70 个源文件，这是对的，不是缺东西。
- 首次上架**建议手动 `git tag 0.1.0`** 而不是 `npm version patch`：
  后者会升到 `0.1.1`，而社区目录初次提交一般用当前版本号。
- `git push` **不会自动推 tag**，必须 `git push origin 0.1.0` 单独执行。

### 又踩了一次：API 推送导致历史分叉

用 Git API 推送会产生**独立的 commit 对象**，本地与远端从共同祖先起分成两条线。
后果是之后 `git push` 报 **non-fast-forward**。

修法（git 自己的机制能处理）：

```bash
git fetch origin
git rebase origin/main
# 冲突时取远端版本（记忆文件两边等价）
git add <文件> && GIT_EDITOR=true git rebase --continue
```

**rebase 自动识别并丢弃了 2 个「patch contents already upstream」的等价提交** ——
内容一样就不重复保留，历史干净了。最终本地=远端=`993b843`，工作区干净。

> 结论：能用 git 传就用 git 传。API 推送是 proxy 挂了时的应急手段，
> 事后要用 rebase 收拾，而且**它绕过了 git 的对象去重**。

## 流水线是什么（用户问的）

GitHub Actions = 放一个 YAML 在 `.github/workflows/`，GitHub 每次遇到对应事件
就自动起一台云端机器跑一遍。

两条流水线：
- `ci.yml` —— 推代码触发，跑测试→构建→产物自检，**只检查不发版**
- `release.yml` —— 推 tag 触发，同样三道检查 + **创建 Release**

**它的真正价值不是省事，是给你一个本机之外的标准环境。**
今天抓出的四个问题（jsdom 未声明、Node 版本、lock 缺平台、分支名写错）
**在本机全都是绿的** —— 本机永远正常，只有换环境才暴露。
判断这类问题最快的办法就是推上去让 CI 跑一遍：
本地再全绿也只有一台机器的信息量。
