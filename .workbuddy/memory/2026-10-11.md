## Clarity Ledger · install.bat 跑不了（行尾符）

用户报 `install.bat` 双击后刷出几十条 `'xxx' 不是内部或外部命令`。

### 根因

**文件是 LF 行尾，而 `.bat` 必须是 CRLF。**

cmd.exe 按 CRLF 切分命令，遇到 LF 会把相邻行**错位拼接**，于是：

```
REM  Clarity Ledger - install into an Obsidian vault (Windows)
```

被截成两半、分别当成命令 → `'larity' 不是内部或外部命令`、`'al' 不是内部或外部命令`。

**报错信息与真实原因隔得非常远** —— 第一反应必然是「脚本内容写错了」，
而内容一个字都没错。这个坑作者自己也在文件头写过注释（编码相关），
但当时只考虑了**编码**、没考虑**行尾**。

这个 bug 本机复现不了：`core.autocrlf=true` 时 git 检出会自动把 LF 转 CRLF，
所以作者自己跑永远正常，只有 clone 下来的人会炸。

### 顺带发现第二个坑：非 ASCII

文件里有一行 `echo Then walk through 手测清单.md` —— 是我上一版加的，
**破坏了原作者「Everything here is deliberately ASCII」的约定**
（.bat 按系统 ANSI 代码页 cp936 读，UTF-8 中文会变乱码）。

讽刺的是我写这次修复说明时，第一版注释里**又写了中文文件名**，
当场被自己的检查脚本抓出来。

### 修法

- `install.bat` 行尾 LF → CRLF（129 行）
- 新增 `.gitattributes` 从根上锁死，不靠各人本机配置：
  `*.bat text eol=crlf`、`*.sh text eol=lf`
- 新增 `scripts/check-bat.mjs`（`npm run check:bat`），五条断言：
  CRLF、无 `\r\r\n`、纯 ASCII、无 BOM、首行 `@echo off`。并入 `npm run build`。

## 顺带修好：lock 的第二类坏条目

`fix-lock-optional.mjs` 早先只处理「连 version 都没有」的空壳，
漏了「有 version 但缺 `resolved`/`integrity`」的那类
（`@csstools/css-tokenizer` 就是这种，npm 要解析 peer 元数据才写得全）。

判据不能只看 `!v.version`。两类都要处理，且情况 B 必须**就地补字段**而非整条替换
——那些条目身上有 `peer: true` 等字段，整条覆盖会让 lock 依然不同步。

本次补了 **130 个条目**（远超原先的 22 个）。

## 写断言脚本时它自己崩了（第二次栽在同一类坑）

`check-bat.mjs` 第一版有 `new Set(x).map(...)` —— Set 没有 map，抛 TypeError。
而这个 TypeError 发生在**构造错误消息的表达式**里，
于是「非 ASCII 检查」这条最该抓乱码的断言自己先崩了、永远报不出结果。

修法：`ok()` 的 detail 改成**传函数**，惰性求值 + try/catch 包住，
构造消息的异常会明确报成「这条断言本身有 bug」。

结论：**错误消息本身也要测**。`{ ok }` 那层包装包不住构造消息的代码。

### 关键事实（写清单时核实的）

- `manifest.version` = `0.1.0`，`versions.json` = `{"0.1.0": "1.5.0"}`，**还没有 tag**
- `main.js` / `styles.css` **故意不在仓库里**（`.gitignore` 明确写了）——
  Release 流水线会现构建。远端只有 70 个源文件，这是对的，不是缺东西。
- 首次上架**建议手动 `git tag 0.1.0`** 而不是 `npm version patch`：
  后者会升到 `0.1.1`，而社区目录初次提交一般用当前版本号。
- `git push` **不会自动推 tag**，必须 `git push origin 0.1.0` 单独执行。

### 又踩了一次：API 推送导致历史分叉

用 Git API 推送会产生**独立的 commit 对象**，本地与远端从共同祖先起分成两条线。
后果是之后 `git push` 报 **non-fast-forward**。

修法（git 自己的机制能处理）：

```bash
git fetch origin
git rebase origin/main
# 冲突时取远端版本（记忆文件两边等价）
git add <文件> && GIT_EDITOR=true git rebase --continue
```

**rebase 自动识别并丢弃了 2 个「patch contents already upstream」的等价提交** ——
内容一样就不重复保留，历史干净了。最终本地=远端=`993b843`，工作区干净。

> 结论：能用 git 传就用 git 传。API 推送是 proxy 挂了时的应急手段，
> 事后要用 rebase 收拾，而且**它绕过了 git 的对象去重**。

## 流水线是什么（用户问的）

GitHub Actions = 放一个 YAML 在 `.github/workflows/`，GitHub 每次遇到对应事件
就自动起一台云端机器跑一遍。

两条流水线：
- `ci.yml` —— 推代码触发，跑测试→构建→产物自检，**只检查不发版**

**它的真正价值不是省事，是给你一个本机之外的标准环境。**

**在本机全都是绿的** —— 本机永远正常，只有换环境才暴露。
判断这类问题最快的办法就是推上去让 CI 跑一遍：
本地再全绿也只有一台机器的信息量。

### 踩的两个坑（都记在代码注释里了）

**坑一：`TFile` 不能改成值导入。**
审核建议用 `instanceof TFile`，改成值导入后**所有测试立刻报**
`Failed to resolve entry for package "obsidian"` ——
`obsidian` 这个包只有类型定义、没有运行时入口（package.json 无 main/module）。
真机上能跑（Obsidian 运行时注入），但测试全挂。

**坑二：store 是纯逻辑层，测试跑在 node 环境（无 `window`）。**

40 条 store 用例全挂，而且报的是运行时错误不是类型错误，容易找错方向。
**改从 `globalThis` 取** —— 它在 node 和浏览器两边都有 `setTimeout`。
类型用 `ReturnType<typeof setTimeout>`（两边各自成立）。

## 社区目录 Error：`createElement('script')` 的真正根因

审核拒了：`Code creates script elements at runtime`（Error，不过审）。

### 社区里已有答案：React 19 的「资源提升」

官方论坛（2026-06）和 dev.to 上有两位开发者踩**完全一样**的坑，
描述的现象一模一样：`main.js` 里**正好 3 处** `createElement("script")`，

原因：React 19 新增的 **Resource Hoisting** 功能——react-dom 内部会为
预加载创建 `<script>` 标签。官方论坛维护者 WhiteNoise 参与讨论。
**解法：降到 React 18。**

### 但这个项目的根因更绕一层：版本不一致

我一开始诊断成「用了 React 19」，但实际是：

| 位置 | react 版本 |
|---|---|
| `package.json` 声明 | 18.3.1 |
| 本机 `node_modules` | 18.3.1 |
| **`package-lock.json`** | **19.3.0** |
| **产物（CI 构建）** | **19.3.0** |

**本机 `npm install` 按 package.json 装 18；CI 的 `npm ci` 按 lock 装 19。**
产物在 CI 上构建 → 用户拿到的是 React 19 版 → 审核报错。

**这是今天早上那四道 CI 门槛的第六次翻版。**
判据不该是「package.json 写了什么」，而是
**「lock 里锁的版本是否满足 package.json 声明的 range」**。

修法：删掉 `package-lock.json` 重新生成（`npm install --package-lock-only`），
再跑 `lock:fix` 补183 个平台条目。产物从 **317 KB → 239 KB**。

### 两次自己犯的错

**一、API 推送时漏文件。**
用 Git API 推送时只选了 `package-lock.json` 和测试文件，
**漏了 `package.json` 本身**（本地早就是 ^18.3.1，远端还是 ^19.0.0）。
CI 立刻报 `Invalid: lock file's react@18.3.1 does not satisfy react@19.0.0`。
→ **API 推送必须用 `git diff --name-only` 核对文件列表，别凭记忆列。**

**二、把产物检查写进了测试里。**

但 CI 是 `npm ci → npm test → npm run build` ——
**跑测试时 `main.js` 是上一版遗留的**。
本机习惯先 build 再 test 所以看不出来。**第七次「本机绿、CI 红」。**

→ **产物检查必须放在 `scripts/verify-build.mjs`**（它本来就在 build 之后跑）。
`alias.test.ts` 只守**输入**：lock 与 package.json 一致、react 是 18。
**输入对了，产物自然对。**

## 0.1.2 发版成功

用户没`git pull` 就直接 `npm version patch`，**结果 package.json 撞进冲突状态（UU）**。
但 tag、manifest、versions.json 全部同步正确，代码没丢。

### 为什么冲突：不是「没 pull」，是 API 推送的副作用

沙箱代理不通，我多次用 Git API 推送。API 推送会生成**独立的 commit 对象**，
本地与远端从共同祖先起分成两条线 —— 提交内容等价但 sha 不同。
用户后续任何 git 操作（pull / push）都会撞上 non-fast-forward 或冲突。

**这是「用 API 绕过 git 传输层」的固有代价**，今天已经遇到四次了。

### 解决过程

1. `git checkout --ours package.json` —— ⚠️ **rebase / merge 语境下 `--ours` 指的是「上游」**，
   不是「我本地」。这里要的是 0.1.2，得用 `--theirs`。
   （直觉上的 ours/theirs 在 rebase 里是反的，踩过。）
2. `git rebase --skip` 跳过远端已有的等价提交
3. **重打 tag** —— 这步最关键：rebase 把 commit 从 `1a7981a` 重写成 `a89b7d9`，
   而 tag 还指着旧的那个。**推 tag 前必须重打**，
   否则流水线构建的是那个已经不在历史里的旧 commit。

|---|---|
| tag | 0.1.0 / 0.1.1 / **0.1.2**（都不带 v） |

| Release 0.1.2 | Published（非 draft），附件 3 个 |

## 社区目录第二次拒绝：lockfile is out of date（根因是我造的）

```
       Please run npm install locally and commit the updated package-lock.json

```

### 根因：`--package-lock-only` 生成的那份 lock 是坏的

今天早上为了修 React 版本不一致，我用了
`npm install --package-lock-only` 重新生成 lock
（因为本机 `npm install` 会挂在 esbuild 的 postinstall 上）。

**那种方式生成的 lock 与真实安装树不一致** ——
npm 会去装一些本不该存在的嵌套副本，
然后卡在它们的 postinstall 上 → `npm ci` 失败。

正确做法：**删掉 lock 和 node_modules，让 npm 在完整安装状态下自己更新**

### ⚠️ 教训：`--package-lock-only` 不能用来「修lock」

它只更新 lock 的元数据，**不保证依赖树结构与真实安装一致**。
本机看不出来（node_modules 是旧的，早就装好了），
只有社区目录在干净环境跑 `npm ci` 才撞出来。

**判断 lock 对不对的唯一办法：干净目录跑 `npm ci`。**
但这台机器跑不了（spawnSync EBUSY），所以**只能靠 CI 验证** ——
这也是为什么每次改 lock 都必须推上去让 CI 跑一遍。

## 复核「第三次拒绝」的三条 Error：根因是 lock 的**字段顺序**（2026-10-11 晚）

主理人拿第三次拒绝的报告来问怎么修。逐条复现后的结论：

### 1. 那份报告是**旧快照**（提交 41ea2af 当时的状态）

证据（可复算）：报告里 `prefer-create-el` 报 SettingsTab.ts **106/107/110**。
今天这三处 `createEl` 调用在 **114/115/118** ——
差的正好是 41ea2af 加进去的那段 8 行注释。
`globalThis` 报 store/index.ts 144/145 + test-setup.ts 39，
也精确等于 0a81301 之前的位置。**报告早于最后两次修复提交。**

### 2. 「The npm lockfile is out of date」的真根因：字段顺序

不是依赖树错 —— **这份 lock 根本不是 npm 写的**。

`scripts/fix-lock-optional.mjs` 处理「有 version 缺 resolved」那类时是**就地补**：
```js
cur.resolved = ...; cur.integrity = ...   // 追加到对象末尾
```
→ 条目字段顺序变成 `version, dev, license, dependencies, engines, resolved, integrity`
而 npm 写的是 `version, resolved, integrity, dev, license, dependencies, engines`。

**JSON 语义逐字段深比较完全相等（220 条全等）**，所以
`npm ci` 能装、CI 绿、本机看不出任何问题；
但审核器是跑一遍 `npm install` 再比 lock 变没变 → 每次判定「过期」。

本机实测：完整 `npm install` 重写 lock = **2035 增 / 2035 删，纯换顺序**。

**修法**：`npm install`（**不加** `--package-lock-only`）→ `npm run lock:fix` 复查。
验证：干净目录 `npm ci` 通过（128 包）；再跑一次
`npm install --package-lock-only` 后 `cmp` **逐字节一致** → lock 已稳定。
已提交 `41b36b8` 并推送。249 条用例全绿。

**教训**：`lock:fix` 这类「就地补字段」的脚本会悄悄改掉 npm 的序列化顺序。
以后 lock:fix 跑完，必须再让 npm 完整重写一次 lock 才算完。

### 3. 用官方 lint 插件把审核警告**本地复现**了

`eslint-plugin-obsidianmd@0.4.2`（Obsidian 官方）+ flat config

| SettingsTab.ts:114,115,118 | `prefer-create-el` | 要用 `createDiv` / `createSpan`，**不是**认错 API |

## 卡片上那个橙色三角 = Scorecard 的「Review: Caution」

### 查法（可复用）

目录站是 Next.js，搜索页客户端渲染、SSR 里什么都没有；
但**作者主页 `community.obsidian.md/users/<handle>` 是服务端渲染的**，
条目卡片的 HTML 直接能 curl 到 —— 徽章的 svg 与 tooltip 文案都在里面：

```html
<span class="group/review relative inline-flex flex-shrink-0 text-orange-400">
  <svg class="lucide lucide-triangle-alert ...">
  <span role="tooltip" ...>Caution</span>
</span>
```

→ 橙色 `triangle-alert`，悬停文案就俩字：**Caution**。

### 它对应什么

插件页 Scorecard 的两行：
- **Health：Excellent（绿）** —— 卫生/维护/响应/采用度
- **Review：Caution（橙）** ← 就是这个三角 = **最新一次对发布版本的自动扫描结果**

明细（从插件页 HTML 里抓的）：**Passed 6 / Disclosures 1 / Warnings 37**。
- Passed 里有「No suspicious network patterns found.」、用到的 Obsidian API（Vault Read）等
- Disclosures 1 条：「Malware scan not available.」
- 37 条 Warning 全是静态分析/代码质量，**没有安全类**：
  `no-unnecessary-type-assertion`（占大头）、`no-misused-promises`、
  `await-thenable`、CSS `Avoid !important`、`Unexpected unknown at-rule`（Tailwind v4）

不阻断安装与上架，但橙标挂在用户能看到的卡片上。

### 附带确认：描述改动已生效

`community-plugins.json` 镜像里那条已经是新描述，**含 认知觉醒** ✅
（后面仍挂着「- This plugin has not been manually reviewed by Obsidian staff.」，
那是人工审核状态，跟自动扫描的 Caution 是两回事。）
